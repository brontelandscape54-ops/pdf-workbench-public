# PDF Workbench の開発経緯と設計思想

本書は、PDF Workbenchを初めて使う方に向けて、**何を解決するために作り、なぜ現在の操作・保存・復元方式を選んだのか**を説明するものです。日々の内部作業記録や全コミットの変更履歴ではありません。現在の操作方法は[README](../README.md)と[画像付きクイックスタート](QUICK_START_JA.md)を参照してください。

## 1. 出発点：固定4分割のOCR前処理

前身となる[ocr-pdf-cut-to-four](https://github.com/brontelandscape54-ops/ocr-pdf-cut-to-four)は、二段組・縦書きのPDFをOCRへ渡す前に、各ページを「右上→右下→左上→左下」などの順で4分割するコマンドラインツールです。分割線の位置、重なり幅、DPI、出力順を指定し、多数のページをまとめて処理できるようにしました。

ところが、実資料のページは均一ではありません。見出し、注、写真、段組の変化、綴じ位置や撮影時のずれなどにより、全ページを同じ位置で切ると文字が分割線に重なる場合があります。コマンドラインの数値を変更して全体を再処理するだけでなく、**実際の紙面を見ながら例外ページを直せる道具**が必要になりました。

PDF Workbenchは、旧CLIのGit履歴を引き継いだものではなく、その用途を出発点として独立に開発したGUIツールです。固定4分割だけで足りる作業には、旧CLIも引き続き利用できます。

## 2. 分割の単位を「ページごとの編集可能な領域」にする

初期構想では「分割なし／上下2分割／4分割」をページ単位で切り替え、プレビュー上の分割線をドラッグする方式を考えていました。しかし、機関紙・新聞などでは、1ページ内でも記事、欄外案内、写真、異なる段組が混在します。

このため、領域を左右または上下へ繰り返し分ける**Custom split（分割木）**に発展させました。4分割と1領域は現在も簡易設定として利用できますが、それぞれを固定モードとして閉じず、作成後も線の移動・領域の追加・統合ができます。分割位置はプレビュー画素数に固定せず、ページに対する相対的な位置として管理し、画面表示と書き出し解像度を分離しています。

各領域の**番号はOCRへ渡す順番**です。紙面上で近い領域を単純に上から順に出力すればよいとは限らないため、領域の形と読み順を分けて保持し、必要に応じて順番を変更できるようにしました。

## 3. 一括作業と例外ページの両立

似た版面が続く場合、毎ページ同じ操作を繰り返す必要はありません。左のサムネイルで複数ページを選んだ状態で中央プレビューを編集すると、**編集が確定したレイアウト**が選択中の非固定ページへコピーされます。複数選択しただけでは、各ページの設定は変わりません。特殊なページを固定すれば、他ページからの一括変更から保護できます。1回の編集で変更した複数ページはまとめてUndo／Redoできます。

一方、「自動分割」では、ページ内の余白を解析して分割候補を作ります。これは中央プレビューの完成形を他ページへ配る手動一括編集とは異なり、**対象ページごとの画像を個別に解析**します。自動判定は確定的な本文構造の認識ではありません。利用者がプレビューで確認し、文字を切る線などを修正する前提です。

中央プレビュー内の分割領域と、左サムネイルのページ選択は別の操作対象です。中央を操作中の⌘A（Windows/LinuxではCtrl+A）は、表示ページの**全領域の選択**に使います。選択だけでは分割設定を変えません。OCR順の振り直しや領域統合などを行うときに利用できます。

## 4. なぜ「分割してOCRした後、元の紙面へ戻す」のか

分割PDFはOCRに適した入力を作るための中間成果物です。読書や参照、原紙面に即した確認のためには、元のページ配置も重要です。そこで、分割時に「どの元ページの、どの範囲に対応するか」を記録する**OCR Bundle**を設けました。

Bundleには外部OCRへ渡す分割PDFと、ページ・領域の対応情報を持つ `manifest.json` を収録します。外部OCRソフトで検索可能PDFを作成した後、WorkbenchがそのPDFのページ内容を元のページ寸法・領域へ配置し直します。Workbench自身はOCR文字認識を実行せず、特定のOCRエンジンにも依存しない設計です。

分割境界に文字がかかる場合への対策として、OCR入力の切り取り領域には重なり幅を持たせられます。一方、復元時に同じ画像が重複しないよう、各領域には復元時に担当する**重ならない範囲**を別途定めています。つまり、OCR用に広めに切り取る範囲と、元ページへ戻す範囲を区別しています。

この方式は万能ではありません。OCRソフトがページの端を切り取ったり、回転・任意の傾き補正をしたり、ページ数・順序を変えたりすると、記録した対応関係に基づく復元ができない場合があります。また、分割境界をまたぐ文字情報の完全な保持は保証できません。**余白を通して分割し、復元後に検索位置と見た目を確認する**ことが重要です。

## 5. Bundleを作業再開にも用いる理由

分割設定を調整し、外部OCRを試し、必要なら分割を直すという作業は一度で終わらない場合があります。別の専用プロジェクトファイルを増やすのではなく、OCR用PDFと復元情報を収めたBundleを**作業再開の単位**にもしました。

`workspace.json` は現在ページ、ページ固定や出力設定などを保持し、`manifest.json` は分割・復元情報を保持します。両者の保存形式は独立して管理し、旧形式を読み込む際は既存のBundleを開いただけで書き換えない方針です。

既存Bundleの更新時は利用者に確認し、Workbench生成ファイルを更新しつつ、追加されたOCR結果やメモなどを引き継ぐ仕組みを設けています。ただし、**古いOCR結果が新しい分割設定と適合するとは限りません。** 分割数・位置・順序を変えた場合は、新しい分割PDFからOCRを実行し直してください。

Bundleを他者に渡す際は注意が必要です。`workspace.json` には元PDFへの**ローカル絶対パス**が含まれ、設定によっては元PDFそのものも同梱されます。共有前に内容と資料の利用条件を確認してください。

## 6. 実資料による分割・OCR・復元の確認（2026年9月22日）

画像化された縦書き機関紙『泉』第26号（元4ページ）について、プレビュー上で領域のOCR出力順を振り直し、分割PDFを外部OCRで処理してから、Workbenchで元の4ページへ復元した。提示された復元後PDFでは紙面の外観と抽出可能な文字情報が確認できた。前回の結果では3ページ目の記事後半が先に抽出されていたのに対し、今回の結果では見出し・「まえがき」から本文へ進む順になった。**領域ごとの出力順を意識した編集が、検索可能PDFからの文章抽出順に関わる**ことを示す使用例である。

ただし、この比較のみで改善の原因を出力順変更だけに限定することはできない。外部OCRの再実行による変動や、領域内部での見出し・写真キャプション等の混入は残る。利用したOCRエンジン名・バージョンは未記録であり、分割境界の文字欠落、テキスト検索位置、OCR精度を全件校合した検証ではない。原紙面やOCRテキストの実物を本公開リポジトリへ収録しない。個別の実機検証と、一般の資料・OCRソフトについての動作保証は区別する。
